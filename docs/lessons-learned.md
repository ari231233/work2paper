# 经验教训与复盘

> 记录 papermine 从 v0.1 确定性管线到 v0.2 六 Agent 闭环的开发过程中，遇到的所有问题、根因、解法与教训。
> 目的：方便日后归纳总结、避免重复踩坑。

---

## 零、复盘要点（速览）

1. **区分"网络问题"和"代码问题"**：本机直连外网被干扰（SSL EOF），几乎所有"看似代码 bug"的问题，根因都是网络，需走代理。
2. **降级路径必须"可见"**：静默降级会让"看起来正常但实际降级"的问题极难排查（LLM 静默降级是典型）。
3. **指标值要追溯来源**：novelty=2.5 是"文献为空无法对拍"，不是"中等新颖"。
4. **改跨模块 schema 前，先查 git 状态**：否则会与已建模块产生 schema 漂移。
5. **任务按模块划分，不按先后**：模块升级 = 模块新版本（M7 v2），不是新任务跨模块改旧模块。
6. **机器特定配置（key/代理端口）只进 `.env`**：功能可开源共享，机器配置必须 gitignore。
7. **调用外部 API 前做规范化**：中文 query 要翻译成英文；URL 会变要 follow_redirects；公开 API 要预判限流。

## 一、网络与环境

### 1.1 直连外网被干扰（本机网络问题）

- **现象**：GitHub、PyPI、清华镜像、DeepSeek、arXiv、Semantic Scholar，直连全部 `SSL EOF` / `Connection reset`。
- **根因**：本机网络出口对直连 HTTPS 有干扰（墙/本地防火墙），与代码无关。
- **解决**：走本地代理 `127.0.0.1:7897`；工具加了 `PAPERMINE_PROXY` 支持（`config.py` 的 `get_proxy/apply_proxy`，写入 `os.environ` 供 httpx trust_env 使用）。
- **教训**：
  1. 排查报错先做"直连 vs 代理"对比，几秒钟定位是否网络问题。
  2. 代理端口是**机器特定配置**，只进 `.env`（gitignored）；`.env.example` 里用注释示例、不能硬编码自己的端口。

### 1.2 Semantic Scholar 429 限流

- **现象**：S2 公开 API 返回 429，检索源被跳过。
- **根因**：无 API key 的公开接口被限流。
- **解决**：退避重试（2 次，1.5s/3s）；后续可配免费 API key。
- **教训**：第三方公开 API 要预判限流，做退避 + 优雅降级（失败跳过该源，不影响主流程）。

## 二、代码 Bug

### 2.1 arXiv 301 重定向

- **现象**：arXiv 检索一直抛异常，`papers` 全空、`sources` 空。
- **根因**：代码用 `http://export.arxiv.org`，arXiv 已 301 跳转到 `https://`，而 httpx 默认不 follow_redirects，`raise_for_status()` 直接抛 301。
- **解决**：`http://` → `https://` + `follow_redirects=True`。
- **教训**：单测用 mock 掩盖了真实网络行为，导致 301 没被发现；外部 API 的 URL/协议会变，要做重定向跟随或直接用 https。

### 2.2 中文 query 检索 0 结果

- **现象**：检索返回 `papers=[]`，文献始终为空。
- **根因**：检索直接发**中文问题描述**给英文库（arXiv/S2）→ 0 结果；且"查询改写为英文"逻辑有**鸡生蛋问题**（只有 `papers` 非空才触发改写，但中文 query 本来就 0 结果 → 永远不触发）。
- **解决**：检索前先用 LLM 把含中文的 query 翻译成英文学术关键词（`_translate_query`）。
- **教训**：调用外部英文 API 前，先做语言规范化；改写的触发条件不能依赖"已有结果"。

### 2.3 httpx 每次调用新建连接（性能）

- **现象**：几十次 LLM/检索调用，每次 `httpx.post/get` 便捷函数都新建 Client + 重做 TLS 握手。
- **根因**：用了 httpx 模块级便捷函数，而非复用 Client。
- **解决**：`DeepSeekProvider` 持有持久 `httpx.Client`；检索层加模块级 `_http()` 复用 Client（连接池 + keep-alive + TLS 复用）。
- **教训**：频繁 HTTP 调用要复用连接池；改实现后单测的 mock 方式（patch `httpx.get` → patch 复用 client）需同步更新。

### 2.4 检索相关性差（英文 query 太泛）

- **现象**：检索返回了 *Byzantine-Resilient SGD*、*dark energy* 等完全无关的论文。
- **根因**：翻译后的英文 query 太泛，arXiv 按词面命中（如 "life" 命中 "LIFE" 望远镜论文），缺乏相关性过滤。
- **解决**：立项 M10——翻译产出更聚焦的关键词、检索加字段约束（`ti:`/`abs:`）、检索后做相关性过滤。
- **教训**：外部检索 API 的"召回"不等于"相关"，要加相关性过滤/后校验。

## 三、设计与理解陷阱

### 3.1 LLM 静默降级（最隐蔽的一个）

- **现象**：配了 key，报告显示 `llm_backend: deepseek`，但输出仍是模板化文本，和没配 key 一样。
- **根因**：`llm_backend` 只表示"用了 DeepSeek provider"，**不代表调用成功**；LLM 调用失败（网络/HTTP/schema）被 Agent 静默捕获，降级到确定性规则，且**没有在报告中标记降级**。
- **教训**：降级路径必须**显式可见**——建议在报告/日志里标记"本段为确定性降级产物 + 降级原因"，否则"看起来正常但实际降级"的问题极难排查。

### 3.2 novelty=2.5 的误读

- **现象**：报告满屏 `novelty=2.5` + `verdict=rework`，一度以为是创新点差。
- **根因**：检索失败 → 文献空 → novelty 无法对拍 → LLM 保守给 2.5 并注明"文献缺失"。
- **教训**：指标值要追溯**来源**（看 evidence）；2.5 是"无法判断"，不是"中等"。

### 3.3 数据可得性"high"的粒度局限

- **现象**：所有点 `data_feasibility=high`。
- **根因**：确定性规则只看 facts 里有没有 data/metrics **标签**（关键词命中），不看真实数据。
- **教训**：MVP 粗判要显式标注局限（"high 仅表示命中标签，不等于真有数据"）。

### 3.4 自进化机制：从"记忆"到"策略"

- **演进**：最初设计是"经验 = 被检索的记忆（few-shot）"，后升级为"经验 = 能改行为的策略"。
- **关键结论**：
  1. 经验条目加 `policy{target, directive}`（结构化策略）+ `effect`（记录有没有真提升）+ `applicability`（适用边界防污染）+ `source_domain` + `principle`（去领域化）。
  2. 生效方式用**混合**：结构化 policy 决定"在哪生效+约束是什么"，LLM 负责"在开放空间执行约束"。
  3. 生命周期 `candidate → active → degraded → retired`，由 `support_count + effect` 驱动。
  4. 跨任务积累 = 去领域化（principle）+ applicability 门控。

### 3.5 LLM 评分趋同

- **现象**：4 个创新点 novelty 全 3.5、工作量全 120，看起来像模板回复。
- **根因**：并非模板（每个 idea 的 `novelty_reason` 其实不同），而是 LLM 评分粒度粗——结构相似的 idea 被给了同一个"中等"档整数分。
- **教训**：LLM 打分有趋同/取整倾向；评估类任务要加"区分度约束"或强制排序。
- **解决**：立项 M11（多维加权评分体系，5 维度各带理由，强制区分度）。

### 3.6 报告渲染缺文献段

- **现象**：文献检索做了（dossier.json 里有 papers + gap_note），但 report.md 里看不到任何文献。
- **根因**：`_render_report_md` 只渲染六段（叙事/问题/创新点/评估/路线图/决策），漏了 literature 段。
- **教训**：**做了证据却不展示 = 白做**；报告渲染要覆盖所有关键证据源。

## 四、工程与流程

### 4.1 schema 漂移（先改文档、后查 git）

- **现象**：重写架构 §3.6 后，才发现 M7 已按旧 schema 建好，文档与代码不一致。
- **根因**：改跨模块 schema 前没有先查 git 状态 / 已建模块。
- **教训**：改动会跨模块波及的内容（§3/§4 schema、接口契约、字段名）前，先 `git status && git log --oneline -10`，发现已有模块依赖它 → 先标记"需协作类迁移"再改文档。已写入 `AGENTS.md` 硬性规则。

### 4.2 任务划分原则（模块 vs 先后）

- **现象**：M8 被设计成"改 M7 的跨模块任务"。
- **教训**：任务按**模块**划分，不按先后；禁止立项新任务去改其他模块的文件；模块需升级 = 该模块的新版本（如 `M7 v2`），由该模块负责。已写入 build-plan §1。

### 4.3 交付自检 + 遗留问题三分流

- **交付自检清单（每框必附）**：改动文件 / 测试结果 / 契约核对 / 降级路径 / 遗留问题。
- **遗留问题三分流**：阻塞类（当场解决）→ 可延后类（进 Issue `deferred`）→ 需协作类（进 Issue 标注依赖模块）。

### 4.4 git 身份占位符

- **现象**：初始提交用了占位身份 `papermine-dev <dev@localhost>`。
- **教训**：上线前需换成真实身份并 `git commit --amend --reset-author`。

## 五、开源准备（清单）

- 许可证（MIT）、免责声明（学术诚信 + 隐私）、双语 README、测试、CI（pytest + 冒烟）、CHANGELOG、贡献指南、行为准则、PyPI 元数据。
- **命名查重**：`papermine` 语义撞车（"挖论文内容" vs "挖论文点"），最终仓库名用 `work2paper`。
- **竞品扫描结论**：精确方向（"自己的横向工作→论文点"）无同款；但"研究想法生成"赛道不空（IdeaMiner / DeepInnovator / open-collider / Scideator 等）。护城河 = 输入侧（项目资产）+ 场景（硕士毕业）+ 自进化经验库。
