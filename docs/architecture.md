# papermine 架构设计文档

> 面向科研领域学生的「横向工作 → 论文点」闭环系统。
> 版本：v0.3（草案）｜ 状态：待实施

---

## 1. 定位与目标

**一句话定位**：一个研究助理型工具，把学生做过的横向/工程工作，转化成**可评估、可追溯的候选论文点**与**论文路线图**。人是驾驶员，系统是副驾驶。**越用越懂科研**（自进化）。

**核心目标用户**：硕士生（毕业发论文压力最大、横向项目多）。

**非目标（明确不做）**：
- ❌ 代写可提交的论文正文
- ❌ 全自动端到端"一键出论文"
- ❌ 声称能保证发表
- ❌ 对模型权重做微调（自进化靠记忆 + 上下文，不靠改权重）

**成功标准（北极星指标）**：学生拿到报告后，能在 1 小时内判断"我该写哪篇论文、缺什么"，而不是面对一堆工程产物无从下手。**次级指标**：同一用户的第 N 次分析质量，明显优于第 1 次（自进化生效的证据）。

---

## 2. 总体架构

系统由**三层 + 单项目共享档案 + 一个自进化层 + 一个编排器**组成。不是单向链，是图 + 共享状态。

```
      ┌───────────────────────────────────────────────────────────────┐
      │      Evolution Layer 自进化层（跨任务、跨项目、持久化）         │
      │  经验库：案例记忆 / 语义记忆 / 校准记忆                          │
      │  ⑦ 经验沉淀 Agent（每次结束蒸馏经验） + 检索注入（每次开始）      │
      └───────────────────────────┬───────────────────────────────────┘
                                  │ 读历史经验 / 写新经验
      ┌───────────────────────────────────────────────────────────────┐
      │      研究档案 Research Dossier（单项目唯一事实源）              │
      └───────────────────────────┬───────────────────────────────────┘
                                  │ 所有 Agent 读写同一份档案
   ┌──────────┬──────────┬──────────┬─────────┬──────────┬──────────┐
   │ ①项目理解 │ ②问题抽象 │ ③知识检索 │ ④创新点生成 │ ⑤可行性评估 │ ⑥路线规划 │
   └──────────┴──────────┴──────────┴─────────┴──────────┴──────────┘
```

### 2.1 分层

| 层 | 组成 | 性质 | LLM |
|---|---|---|---|
| L0 确定性层 | 资产扫描、AST 解析、关键词抽取、脱敏 | 纯本地、可复现、零成本 | 无 |
| L1 理解抽象层 | ① 项目理解、② 问题抽象 | 结构化 + LLM 理解 | 需要 |
| L2 检索创新层 | ③ 知识检索、④ 创新点生成 | agentic（有循环） | 需要 + 工具 |
| L3 评估规划层 | ⑤ 可行性评估、⑥ 路线规划 | 证据驱动判断 | 需要 |
| **Evolution Layer** | ⑦ 经验沉淀 + 经验库 + 检索注入 | **跨任务、持久化** | 需要 |

### 2.2 闭环反馈边（不是环形，是三条定向回退）

1. **③ ⇄ ④（核心闭环）**：创新点靠文献检验 novelty，检索方向靠候选点引导。二者反复打磨。
2. **⑤ → ② / ④（可行性回炉）**：评估为"需回炉"时，回退到问题抽象或创新点生成。
3. **⑥ → ①（数据缺口回填）**：路线图暴露"缺实验/缺数据"时，回补项目事实。

### 2.3 人类在环检查点

在每个价值跃迁点插入人工确认（**默认暂停，等待确认**）：

| 检查点 | 位置 | 学生确认什么 |
|---|---|---|
| ☑1 | ① → ② | 项目理解是否准确 |
| ☑2 | ② → ③ | 抽象出的研究问题是否认可 |
| ☑3 | ④ → ⑤ | 候选创新点是否认可 |
| ☑4 | ⑤ → ⑥ | 评估结论是否接受 |
| ☑5 | ⑥ 结束 | 最终路线图是否采纳 |

> 检查点决策（accept/rework/note）同时是**自进化层的 F1 反馈通道**（见 §3.3）。

## 3. 自进化层 Evolution Layer

### 3.1 目标

让系统**跨任务、跨项目积累经验**：一次分析结束后总结教训，影响未来所有分析任务。这是从"工具"变成"数据飞轮/护城河"的关键——每个用户/实验室的经验库是私有资产，别人拿不走。

### 3.2 三种记忆

| 记忆类型 | 内容 | 用途 |
|---|---|---|
| 案例记忆 episodic | 完整历史运行（Dossier 快照 + 结果 + 人类决策） | 检索相似案例，做 few-shot 注入 |
| 语义记忆 semantic | 跨案例提炼的模式/规则/教训 | 注入 prompt 指导原则、更新词典与打分权重 |
| 校准记忆 calibration | 评估预测 vs 实际结果的统计 | 校准 ⑤ 的打分，纠正系统偏差 |

### 3.3 三条反馈通道（谁在教系统）

- **F1 人类反馈（主）**：检查点的 accept / rework / note。已选定"暂停等确认"，天然免费、质量高。
- **F2 过程信号（辅）**：回炉次数、收敛轮数、降级次数、检索命中率。
- **F3 结果信号（后期）**：论文是否发表 / 被采纳 / 被拒。

### 3.4 三种进化机制（"进化"具体发生在哪）

- **M1 检索注入**：新任务开始时，按相似度（六元组/场景/任务）检索 top-k 历史案例，作为 few-shot 注入 ②③④⑤⑥ 的 prompt。
- **M2 模式蒸馏**：定期（每 N 次运行或人工触发）由 ⑦ 把案例蒸馏成"指导原则"，写回 prompt 模板、关键词词典、打分权重。
- **M3 评估校准**：用 F3 结果校准 ⑤，纠正系统性偏差（如持续高估 novelty）。

### 3.5 三条护栏（防退化）

1. **进化的是记忆 + 上下文，不是模型权重**：MVP 不做微调，避免模型崩溃、保持可解释可回溯。
2. **提炼后写入，不堆砌**：⑦ 只输出"经验条目"，带置信度 + 验证次数，达到阈值才进语义记忆；坏经验可人工剔除、可回滚。
3. **反馈主源是人类，不是 LLM 自评**：避免自偏好放大错误。

### 3.6 经验条目 schema

```jsonc
{
  "experience_id": "exp_001",
  "type": "pattern",                       // pattern | example | calibration
  "scope": "task:异常检测",                // global | domain:工业时序 | task:...
  "trigger": "项目含工业时序 + 传感器数据 + LSTM",
  "insight": "剩余寿命预测几乎总能抽象成可发表问题",
  "action": "问题抽象时优先考虑 RUL 方向",
  "confidence": 0.8,
  "support_count": 3,                      // 被几次验证才够格进语义记忆
  "source_runs": ["run_1", "run_2"],
  "created_at": "...", "updated_at": "..."
}
```

### 3.7 ⑦ 经验沉淀 Agent（Reflection / Consolidation）

- **职责**：每次分析结束后，把本次运行蒸馏成候选经验条目。
- **输入**：Dossier 快照 + 人类决策记录 + F2 过程信号。
- **输出**：`experience_entries[]`（status = candidate）。
- **时机**：⑥ 结束后自动触发一次；也可人工触发。
- **晋升门槛**：候选条目经人工确认或 `support_count >= 阈值` 后才进入语义记忆，参与 M1 检索注入。

## 4. 研究档案 Dossier（单项目骨架）

Dossier 是**单项目唯一事实源**，所有 Agent 只通过它读写。每条数据带 `provenance`，保证可追溯。

```jsonc
{
  "meta": {
    "project_id": "uuid",
    "version": 3,
    "llm_backend": "deepseek",
    "prompt_versions": { "abstract": "v1", "generate": "v1" }
  },
  "assets": {                            // ← ① 产出
    "facts": { "tasks": [], "methods": [], "data": [], "scenarios": [], "metrics": [], "libraries": [], "modules": [] },
    "narrative": "……",
    "evidence": [ {"source": "README.md", "snippet": "..."} ]
  },
  "problems": [                          // ← ② 产出
    { "problem_id": "p1", "title": "...", "formulation": "...", "motivation": "...", "why_not_engineering": "...", "evidence_refs": [] }
  ],
  "literature": [                        // ← ③ 产出
    { "query": "...", "papers": [], "gap_note": "...", "sources": ["arxiv", "semantic_scholar"] }
  ],
  "ideas": [                             // ← ④ 产出
    { "idea_id": "i1", "claim": "...", "novelty_hypothesis": "...", "problem_ref": "p1", "literature_refs": [], "status": "pending_eval" }
  ],
  "evaluations": [                       // ← ⑤ 产出
    { "idea_ref": "i1", "novelty_score": 3.5, "data_feasibility": "high", "workload_hours": 60, "venue_guess": "...", "verdict": "proceed", "rework_reason": null, "evidence": [] }
  ],
  "roadmap": {                           // ← ⑥ 产出
    "selected_idea": "i1", "paper_type": "方法论文", "outline": [], "experiment_plan": [], "timeline": {}, "missing_items": []
  },
  "human_decisions": [                   // ← 检查点记录（F1 反馈源）
    { "checkpoint": "cp2", "decision": "accept", "note": "问题 1 认可", "ts": "..." }
  ]
}
```

**设计原则**：provenance 强制（LLM 结论必须挂证据，禁止凭空断言）；append-only + 版本号（可回溯）；可重放（同一 dossier 版本 + prompt 版本 → 可复现）。

## 5. 六个 Agent 详细设计

> 约定：每个 Agent 输出绑定 JSON Schema，用 function-calling / JSON mode 保证可解析；解析失败重试，仍失败则降级到确定性规则（§8）。

### ① 项目理解 Agent
- **职责**：项目目录 → 结构化事实 + 项目叙事。
- **工具**：L0 确定性扫描（复用 `scanner.py` / `extractor/` / `knowledge.py`）。
- **LLM 角色**：只做理解与概括；输入是脱敏后的结构化事实，输出 `narrative` + 事实语义纠偏。
- **隐私**：云端 API 不收完整源码，只收脱敏 facts + 必需片段。

### ② 问题抽象 Agent
- **职责**：工程任务 → 可研究问题。
- **关键约束**：每个问题必须输出 `why_not_engineering`，用反例思维过滤伪问题。
- **自进化**：接收 M1 注入的相似案例，参考"过去这类项目抽象出了什么好问题"。

### ③ 领域知识检索 Agent
- **职责**：候选问题/创新点 → 文献图谱 + gap 笔记。
- **工具**：arXiv API、Semantic Scholar、DBLP、（可选）知网。**优先级：arXiv / Semantic Scholar 优先，知网后置。**
- **agentic**：查询改写循环（初始 query → 判断相关性 → 改写 → 再检索，最多 N 轮）。

### ④ 创新点生成 Agent
- **职责**：问题 + 文献 gap → 带 novelty 假设的候选创新点。
- **关键约束**：每个 idea 必须引用 `literature_refs` 并写 `novelty_hypothesis`，禁止无引用空想。

### ⑤ 可行性评估 Agent
- **职责**：**证据驱动**打分，不是 LLM 自评。

| 维度 | 证据来源 | 谁算 |
|---|---|---|
| novelty | `literature.gap_note` 对拍 | LLM 解释 + 检索事实 |
| 数据可得性 | `assets.facts.data` / `metrics` | 确定性规则 |
| 工作量 | idea 复杂度 + 证据量 | LLM 估计（带区间） |
| 档位匹配 | 检索论文的 venue 分布 | 规则 + 静态档位库 |
| 风险 | metrics / baseline 缺失 | 规则 |

- **自进化**：M3 校准——若历史结果持续高估/低估，自动调整打分基准。

### ⑥ 论文路线规划 Agent
- **职责**：评估通过的 idea → 可执行论文路线图。
- **输出**：`roadmap`（selected_idea / paper_type / outline / experiment_plan / timeline / missing_items）。
- **缺口回填**：`missing_items` 非空 → 触发 ① 或标记"待采集"。

## 6. 编排器 Orchestrator

显式状态机（而非 Agent 自由互调，保证可控可测）：

```
UNDERSTAND ──☑1──> ABSTRACT ──☑2──> RETRIEVE <==> GENERATE
                                            │
                                        ☑3 ↓
                                      EVALUATE ──(rework)──> 回 ABSTRACT / GENERATE
                                            │
                                        ☑4 ↓
                                        PLAN ──(missing)──> 回 UNDERSTAND
                                            │
                                        ☑5 ↓
                                      REFLECT(⑦) ──> 写入经验库 ──> DONE
```

实现要点：每状态 = 一个 Agent 调用 + 一次 Dossier 写入；检查点默认暂停等待人工输入（可 `--auto` 跳过）；回退有最大轮数限制，超限降级为确定性报告兜底；⑦ 在 DONE 前执行一次。

## 7. 技术选型（已定）

| 项 | 选择 | 状态 |
|---|---|---|
| 语言 | Python ≥ 3.8 | 已定 |
| LLM 后端 | **DeepSeek**（OpenAI 兼容） | ✅ 已定 |
| LLM 抽象 | 自研 `LLMProvider` 接口 | 已定（可插拔） |
| 结构化输出 | function-calling / JSON mode + Schema 校验 | 已定 |
| 编排 | 自研轻量状态机 | 已定 |
| 检索 | arXiv / Semantic Scholar 优先，知网后置 | ✅ 已定 |
| 存储 | 本地 JSON（Dossier + 经验库） | 已定 |
| 检查点 | **暂停等确认** | ✅ 已定 |
| 依赖策略 | 仅新增 HTTP + 可选 pydantic | 已定 |

### LLMProvider 接口

```python
class LLMProvider(Protocol):
    def complete(self, system: str, user: str,
                 schema: dict, temperature: float = 0.2) -> dict:
        """返回符合 schema 的结构化 dict；解析失败抛 SchemaError。"""
```

- `DeepSeekProvider`：默认实现。
- `OllamaProvider`：后续本地降级方案（同一接口）。
- `NullProvider`：无 API 时回退确定性规则 → 仍出基础报告（离线保底）。

## 8. 可靠性设计

| 风险 | 对策 |
|---|---|
| 多段 LLM 链错误累积 | 结构化 schema 交接（逐节点校验）；关键判断多采样投票；确定性层与 LLM 层分离 |
| LLM 自评不可靠（⑤） | 评估必须挂证据，novelty 只能"对照文献" |
| 结构化输出解析失败 | 重试 → 降级确定性规则 → 标记"低置信" |
| 检索限流/失败 | 本地缓存 + 指数退避；不影响确定性环节 |
| 结论不可追溯 | provenance 强制 |
| **经验库污染/漂移** | 提炼后写入 + 置信度门槛 + 人工剔除 + 可回滚（§3.5） |

---

## 9. 隐私与安全（云端 API 前提）

- **最小化上传**：L0 本地完成，云端只收"结构化事实 + 必需片段"，不收完整源码/原始数据。
- **脱敏网关**（本地正则，可配置）：过滤密钥/token/密码/内网地址/真实公司名/个人信息。
- **用户可控**：`--redact` 开关；未来切 `OllamaProvider` 完全离线（接口已抽象）。
- **审计**：记录每次 API 调用上传了什么（脱敏后）到本地日志。

---

## 10. 学术诚信边界（硬约束）

- ✅ 产出：候选点、评估、路线图、写作框架（至 related work 骨架）、证据链。
- ❌ 不产出：可直接提交的正文、虚构引用、伪造指标。
- 所有结论可追溯到 dossier 证据；报告显著提示"需人工核验与改写"。

## 13. 主要风险

1. **问题抽象质量**（② 是卡点）：伪问题多。对策：`why_not_engineering` 强制 + ☑2 确认 + M1 相似案例。
2. **novelty 判断不可靠**：检索不全误判"没人做过"。对策：多源检索 + 附证据 + 标"低置信"。
3. **云端隐私顾虑**：对策：脱敏网关 + 最小化上传 + 可切本地。
4. **范围失控**：想做"自动写论文"。对策：§10 硬边界 + 非目标清单。
5. **自进化失控**：经验污染、模型漂移、自偏好放大。对策：§3.5 三条护栏。

---

## 14. 已定决策

1. ✅ LLM 后端：**DeepSeek**（OpenAI 兼容）。
2. ✅ 检索源优先级：**arXiv / Semantic Scholar 优先，知网后置**。
3. ✅ 人类检查点：**暂停等确认**。
4. ✅ 自进化：Evolution Layer（§3）已纳入架构；MVP 用"经验库 + 检索注入"，不做权重微调。

## 15. 分发形态（核心引擎 + 多外壳）

**决策**：系统 = 一个核心引擎（Python 库 + CLI）+ 多个薄外壳；**不是**把 CLI 改成插件。

```
核心引擎（本地，唯一真相）
├── 确定性扫描 + 6-Agent 编排 + 自进化层 + 本地存储
└── 外壳（同一个核心，按需叠加）
     ├── CLI          现状：脚本 / CI / 极客用户
     ├── MCP Server   把 6 个 Agent 暴露成工具，供任意 agent / 编辑器调用
     └── Skill        prompt + 指令，教宿主 agent 按流程编排上述工具
```

- **MCP = 给 agent「工具」**（真代码，状态留在本地）；**Skill = 给 agent「方法」**（流程编排指令）。二者组合使用。
- 核心必须**先做扎实**（Phase 1–3），MCP / Skill 外壳在核心稳定后再叠加。
- 原则：核心只写一份；外壳是薄适配层，**不承载业务逻辑**。
